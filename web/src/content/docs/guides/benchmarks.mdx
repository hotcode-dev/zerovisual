## Executive Summary

To evaluate ZeroVisual in realistic production settings, we conducted an empirical benchmark using a real local Vision-Language Model (`google/gemma-4-26B-A4B-it` served via vLLM) across 11 diverse web UI visual regression scenarios (both real-world websites and component-level regressions).

ZeroVisual crops visual failure diffs, aligns them to native Vision Transformer (ViT) patch grids, and converts them to optimized WebP format—achieving dramatic reductions in token overhead and latency while improving triage accuracy.

| Core Metric | Without ZeroVisual (Raw Viewport) | With ZeroVisual (Optimized) | Empirical Improvement |
| :--- | :--- | :--- | :--- |
| **Vision Image Tokens (ViT)** | **9,030 tokens** | **2,838 tokens** | **-68.6% ViT Token Reduction** |
| **Network Payload Transfer** | **638.9 KB** | **116.2 KB** | **-81.8% Bandwidth Reduced** |
| **Total Tokens Consumed** | **7,612 tokens** | **7,148 tokens** | **-6.1% Total Tokens Saved** |
| **Average Roundtrip Latency** | **8.4 seconds** | **7.3 seconds** | **13% Faster Latency** |
| **Average Triage Accuracy** | **59.1%** | **65.5%** | **+6.4% Accuracy Improvement** |

## Benchmark Methodology

### Evaluated Model & Architecture
- **Model:** `google/gemma-4-26B-A4B-it` running locally via vLLM
- **API Protocol:** Standard OpenAI-compatible `/v1/chat/completions` endpoint
- **Vision Grid:** Gemma 4 multimodal native patch grid / model-aligned tiles (768px native tile)

### Evaluation Rubric
Each response is scored against ground-truth metadata across three dimensions:
1. **Target Element Identification:** Did the model identify the exact offending DOM component?
2. **Defect Classification:** Did the model diagnose the visual defect type (layout shift, contrast violation, flex collision, etc.)?
3. **Probable Root Cause & Fix:** Did the model deduce the correct CSS property (margin, z-index, font-size, outline) and offer a working fix?

---

## Key Architectural Insights

### 1. Vision Token Allocation (ViT Patch Math)
Without ZeroVisual, full-viewport screenshots (1280×800) consume **1,032 image tokens** (a 2×2 grid of 768px tiles) per query. With ZeroVisual's bounding-box isolation and patch-aligned downscaling, image tokens drop to a single native tile (**258 tokens**)—a **75.0% reduction** on every desktop screenshot.

### 2. Eliminating Canvas Hallucinations
In complex mobile pages like MDN Web Docs, feeding the full viewport caused the model to struggle with low-contrast elements amidst page clutter (scoring only 30%). Isolating the search input with 32px padding boosted diagnostic accuracy to **65%**. On mobile Wikipedia, accuracy jumped from **0% to 35%**.

### 3. Reasoning Latency
Full-size images impose substantial overhead during multi-head cross-attention. On Real-World Wikipedia Desktop, response latency dropped from **11.3s to 7.2s** (a **37% speedup**), preventing client request timeouts and token exhaustion.

## Running the Benchmarks Locally

The benchmark dataset and automated test runner are included in the ZeroVisual repository:

```bash
# Generate the benchmark image dataset (synthetic + live websites)
npm run benchmark:dataset

# Run the empirical benchmark suite against your LLM endpoint
npm run benchmark
```

Configuration is handled via `benchmark/.env`:

```bash
OPENAI_BASE_URL=https://spark.ntsd.dev:8001/v1
AGENT_MODEL=google/gemma-4-26B-A4B-it
```
